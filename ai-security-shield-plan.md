# AI Security Shield — Implementation Plan

## Approved Decisions
- React app lives directly at `src/` (not `src/frontend/`)
- Dark modern cybersecurity / SOC UI (dark background, red/amber danger accents)
- Simulated data only — no backend, no database, no microservices
- Demo must work without an IBM Bob API key (reliable fallback summary)
- AI explanation is prominent on the Incident Detail page (shown early, before raw signal list)
- Priority: working end-to-end demo first, extra features only if time permits

## Top-Level Overview

**Goal:** Build a polished, end-to-end cybersecurity MVP called **AI Security Shield** that ingests simulated security signals, correlates them into incidents, scores their risk, explains what happened in plain language, and surfaces a prominent user-facing Security Shield warning — all inside a one-day hackathon timeline.

**Scope:**
- React + Vite single-page application (no separate backend needed; all logic runs in the browser with simulated JSON data)
- Pure client-side correlation, risk scoring, and explanation generation
- One prebuilt demo scenario with five correlated signals
- IBM Bob integrated as the AI explanation layer (called from the frontend via the Bob SDK/API)
- All sample data is static JSON files — no real databases, no external APIs, no cloud infrastructure

**Non-goals:**
- Real threat feeds or live data ingestion
- User authentication / multi-tenancy
- Persistent storage beyond browser session
- Any offensive security capability

**Repository constraint:** All source code goes inside `src/`. The existing template files (`docs/`, `demo/`, `presentation/`, `submission.yaml`, `README.md`) must be filled in but NOT deleted or restructured.

## Data Model

### NormalizedSignal
```
id: string
timestamp: ISO-8601 string
source: "email" | "url" | "auth" | "endpoint" | "threat-intel"
severity: "low" | "medium" | "high" | "critical"
title: string
description: string
indicators: {
  user?: string
  device?: string
  ip?: string
  domain?: string
  url?: string
  emailSender?: string
  hash?: string
}
raw: object   ← original simulated signal
```

### Incident
```
id: string
createdAt: ISO-8601 string
signals: NormalizedSignal[]
riskScore: number         ← 0–100
riskLevel: "LOW" | "MEDIUM" | "HIGH" | "CRITICAL"
scoreBreakdown: ScoreBreakdown
correlationReason: string[]
techniques: TechniqueTag[]
status: "active" | "investigating" | "resolved"
aiSummary: string         ← generated by IBM Bob
recommendedAction: string
```

### ScoreBreakdown
```
severityScore: number
signalCountScore: number
threatIntelScore: number
confidenceScore: number
timeProximityScore: number
total: number
explanation: string[]    ← one sentence per factor
```

### TechniqueTag
```
id: string        ← e.g. "T1566"
name: string      ← e.g. "Phishing"
tactic: string    ← e.g. "Initial Access"
```

## Subtask 5 — Correlation Engine

**Status:** `[ ]` pending

**Intent:** Write the logic that groups related `NormalizedSignal` objects into `Incident` drafts by finding shared indicators and time proximity.

**Expected Outcomes:**
- `src/engine/correlator.ts` exports `correlateSignals(signals: NormalizedSignal[]): CorrelatedGroup[]`
- The five demo signals are grouped into a single `CorrelatedGroup`
- Background signals form separate smaller groups or singletons
- Each group includes a `correlationReason` string array explaining why signals were grouped

**Correlation Rules (applied in order, any match = same group):**
1. Same `user` indicator
2. Same `device` indicator  
3. Same `ip` indicator
4. Same `domain` indicator
5. Time proximity: signals within 60 minutes of each other that share at least one indicator
6. Union-Find / transitive closure: if A matches B and B matches C, all three are in the same group

**Todo List:**
1. Create `src/frontend/src/engine/correlator.ts`
2. Implement a simple Union-Find (or array merging) over signals
3. Check each pair of signals for shared indicators
4. Apply time-proximity check as a secondary rule
5. Produce `CorrelatedGroup[]` with `signals[]` and `correlationReason[]`
6. Verify the five demo signals collapse into one group

**Relevant Context:**
- All logic is pure functions — no React, no side effects
- Correlator is called once when the app loads, not on every render

## Subtask 6 — Risk Scoring Engine

**Status:** `[ ]` pending

**Intent:** Assign a transparent 0–100 risk score to each correlated group.

**Expected Outcomes:**
- `src/engine/riskScorer.ts` exports `scoreIncident(group: CorrelatedGroup): ScoreBreakdown`
- The demo scenario scores 85–95/100 (CRITICAL)
- `ScoreBreakdown.explanation` contains 3–5 human-readable sentences explaining each factor

**Scoring Formula (100 points total):**

| Factor | Max Points | Logic |
|---|---|---|
| Highest severity in group | 30 | critical=30, high=22, medium=12, low=5 |
| Signal count | 20 | 1=5, 2=10, 3=15, 4+=20 |
| Threat-intel match present | 20 | yes=20, no=0 |
| Confidence (distinct indicator types) | 15 | 1 type=5, 2=8, 3=12, 4+=15 |
| Time proximity bonus | 15 | all within 30min=15, 60min=10, 120min=5, >120=0 |

**Risk Level thresholds:**
- 0–25: LOW
- 26–50: MEDIUM
- 51–75: HIGH
- 76–100: CRITICAL

**Todo List:**
1. Create `src/frontend/src/engine/riskScorer.ts`
2. Implement each scoring factor as a separate named function
3. Sum factors into total score
4. Derive risk level from threshold table
5. Generate explanation strings per factor (e.g., "Threat intelligence match adds 20 points — this IP is known-malicious")
6. Verify demo scenario scores CRITICAL

**Relevant Context:**
- `ScoreBreakdown` type defined in Subtask 2
- Scoring must be deterministic and re-runnable
